# AGENTS.md — Load Balancer для сети автомоек

Этот файл предназначен для AI-агентов, работающих с проектом. Читатель ничего не знает о проекте заранее.

## 1. Обзор проекта

Проект — **интеллектуальная система балансировки нагрузки (Load Balancer) для сети автомоек**, расположенных на территории одного крупного промышленного предприятия. Водители корпоративного транспорта (легковые, грузовые, автобусы) направляются на мойку; система-диспетчер для каждой заявки выбирает оптимальную мойку, минимизируя суммарное время водителя:

```
T_total = T_travel + T_wait + T_service
```

Цели системы: минимизировать среднее время ожидания, избегать простоя и перегрузки отдельных моек, учитывать приоритеты заявок и совместимость ТС с мойкой, быть устойчивой к пиковым нагрузкам (смены, обеды, пятницы).

**Язык документации и комментариев проекта — русский.** Продолжайте писать документацию и комментарии на русском языке. Технические термины (JSQ, Erlang C, Little's Law и т.п.) остаются на английском, как принято в существующих документах.

## 4. Архитектура системы (из раздела 6 спецификации)

**Архитектурный принцип — Core-First (D-1):** вся предметная логика живёт в `packages/core` — чистом TypeScript-пакете без зависимостей от UI, сети и БД. Симулятор и production-диспетчер — две оболочки над одним ядром. Правило зависимостей: `simulator → core`, `api → core`, обратных нет. В `core` запрещены `Math.random()`, DOM, `window`, `fs` (NF-10, NF-11).

Компоненты:

1. **Request Source** — API или ручной ввод заявок на мойку; в симуляторе — CSV или генератор с seed.
2. **Dispatcher (Core)** — принимает заявку, фильтрует мойки по совместимости **до** вызова алгоритма (F-07), выбирает мойку с минимальным `Score`, резервирует её (`n_transit += 1`), пишет в журнал решений (F-09). Решение < 100 мс (NF-01).
3. **Algorithm Engine (Pluggable)** — реализации интерфейса `LoadBalancingAlgorithm` (раздел 7.1 спецификации; NF-09: замена алгоритма без изменения ядра).
4. **Simulation Engine (DES)** — дискретно-событийная симуляция: события `ARRIVAL`, `WASH_ARRIVED`, `SERVICE_START`, `SERVICE_COMPLETE`, `POST_FAILURE`, `POST_RECOVER`. НЕ дискретное время.
5. **State & Metrics** — длины очередей, занятые посты, `n_transit`, исторический λ, расчёты Erlang C.
6. **Visual Simulator (Frontend)** — Canvas-карта, дашборды метрик, A/B-сравнение алгоритмов, replay исторических данных.

## 5. Алгоритмы балансировки (раздел 7 спецификации)

Порядок важности (по `load_balanser_list.md` и спецификации):

| Алгоритм | Роль |
|---|---|
| Random | Baseline для сравнения — любой осмысленный алгоритм должен его превосходить |
| Round Robin | Статическое распределение, учебная ступень |
| JSQ (Join Shortest Queue) | `argmin(queue + busy + in_transit)` — классика теории очередей |
| **Weighted JSQ** ⭐ | Основной production-алгоритм: `(queue + busy + in_transit) / c · (1/μ̄) + w_travel · T_travel` |
| **Power of d Choices (d=2)** ⭐ | Выбор лучшего из 2 случайных кандидатов (через seeded RNG) |
| **State-Aware Score** ⭐ | `α·W_q + β·T_travel + γ·(1/μ̄) + δ·ρ + ε·penalty`, веса настраиваемые |
| Predictive | Будущее развитие: прогноз нагрузки на 10–30 мин вперёд |

Математическая основа: каждая мойка — система **M/M/c** (Пуассоновский поток λ, экспоненциальное обслуживание μ, c постов) как первое приближение; реальность ближе к **M/G/c**, т.к. время мойки зависит от типа ТС (седан ~8 мин, грузовик ~25 мин, автобус ~40 мин) — поэтому в модели данных `serviceTimeMin` по типам, а в аналитических оценках используется эффективная μ̄ (гармоническое среднее). Вероятность ожидания — **формула Erlang C** (раздел 3.3 и Приложение А спецификации); связь длины очереди и времени ожидания — **закон Литтла** `L = λW`. Условие стабильности: `ρ = λ/(cμ) < 1`.

Все алгоритмы, учитывающие очередь, обязаны включать `n_transit` (машины в пути к мойке) — это защита от herd-эффекта (раздел 7.3 спецификации).

Ключевые модели данных (TypeScript-интерфейсы `CarWash`, `Vehicle`, `WashRequest`, `WashState`, `SimConfig`) и CSV-форматы (`arrivals.csv`, `washes.csv`, `decisions.csv`) определены в разделе 8 спецификации — используйте их как контракты.

## 6. Сборка, запуск и тестирование

**Фактические команды:**

```bash
# Установка зависимостей
pnpm install

# Тесты ядра
pnpm -r test
# или с покрытием
pnpm --filter @loadbalancer/core test:coverage

# Headless-прогон сравнения трёх алгоритмов (seed по умолчанию 42)
pnpm --filter @loadbalancer/core run:headless 42

# Сборка симулятора
pnpm --filter @loadbalancer/simulator build

# Запуск dev-сервера симулятора
pnpm --filter @loadbalancer/simulator dev
```

Известные ограничения текущей версии:
- в `test:coverage` не покрыты все edge-case ветви (например, `Rng.sample`, отказ/нереализованные приоритетные очереди) — см. отчёт покрытия;
- State-Aware Score, Power of d, Round Robin, Least Connections, приоритетные очереди (F-06), отказы постов (F-08) и REST API — Этапы 2–5.

Планируемая стратегия валидации (из разделов 11–12 спецификации):

- **Симулятор как инструмент тестирования**: прогон одного и того же набора исторических данных (CSV) и одного seed через разные алгоритмы и сравнение метрик (A/B-режим).
- **Детерминизм (NF-10)**: два прогона с одним `SimConfig.seed` обязаны давать идентичный `decisions.csv`.
- Генерация тестовых arrivals нестационарным Пуассоновским процессом с суточным профилем — см. Приложение Б спецификации (thinning-метод Льюиса).
- Валидация математики (раздел 12.3): unit-тесты Erlang C против табличных значений (λ=8/μ=5/c=2 → P_wait=0.711; 12/5/3 → 0.647; 16/5/4 → 0.596); сходимость эмпирических `W_q`, `L_q` длительного прогона к теоретическим в допуске ±5% на однородном потоке.
- Целевые KPI: среднее ожидание < 5 мин, максимальное < 15 мин, доля нарушений SLA (W_q > 15 мин) < 5%, средняя загрузка ρ = 70–85%, Jain's fairness > 0.8.

## 7. Соглашения по разработке

- **Следуйте плану разработки** (раздел 11 спецификации), порядок строго core-first: Этап 1 — сначала `packages/core` (домен, PRNG, Erlang C, DES-движок, диспетчер, 3 алгоритма: Random, JSQ, Weighted JSQ) с тестами и headless-прогоном, затем React-оболочка (Canvas-рендер, метрики, control bar) → Этап 2 — расширение алгоритмов → Этап 3 — математическая точность → Этап 4 — прогнозирование → Этап 5 — production-диспетчер с REST API.
- **Модульность алгоритмов обязательна** (NF-09): каждый алгоритм — отдельная реализация интерфейса `LoadBalancingAlgorithm` (раздел 7.1 спецификации); переключение алгоритма в runtime (F-05). Алгоритм получает только совместимых кандидатов — фильтр F-07 применяется ядром до вызова.
- **Детерминизм обязателен** (NF-10): никакого `Math.random()` и `Date.now()` в `packages/core` — только инжектированный seeded PRNG и симуляционные часы.
- **Не выходите за границы системы** (раздел 1.3): биллинг, IoT-управление мойками, GPS-трекинг, мобильные приложения, видеонаблюдение и preemption начатой мойки — вне скоупа.
- Каждое решение диспетчера логируется (F-09) — журнал решений нужен для A/B-анализа и отчётов.
- Диаграммы в документации выполняются ASCII-артом в fenced-блоках ```text, формулы — в нотации LaTeX (`$$...$$`). Придерживайтесь этого стиля при редактировании docs.

## 8. Соображения безопасности и качества данных

- Система работает внутри одного предприятия; внешние угрозы не являются предметом текущей спецификации, но API (этап 5) должен валидировать входные заявки (тип ТС, приоритет, координаты).
- Критичная инварианта устойчивости: мойка с `ρ ≥ 1` нестабильна — алгоритмы обязаны учитывать перегрузку (штраф за `ρ > 0.9` в State-Aware Score) и обрабатывать отказы постов с перераспределением (F-08).
- Совместимость ТС и мойки (F-07) — жёсткое ограничение: нельзя направить грузовик/автобус на мойку, которая его не обслуживает, независимо от score.

| Символ | Значение |
|---|---|
| λ | Интенсивность поступления заявок (машин/час) |

| c | Число параллельных постов мойки |

| DES | Discrete-Event Simulation — дискретно-событийная симуляция |
