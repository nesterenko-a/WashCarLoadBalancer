## 1. Общие положения

### 1.1 Цель документа

Настоящий документ является техническим заданием (ТЗ) и спецификацией архитектуры системы балансировки нагрузки для сети автомоек, расположенных на территории одного крупного промышленного предприятия. Документ определяет:

- математическую модель системы;
- функциональные и нефункциональные требования;
- архитектуру и компоненты системы (в первую очередь — **ядро**);
- алгоритмы балансировки с обоснованием выбора и контрактом плагинности;
- спецификацию визуального симулятора для валидации гипотез;
- стек технологий, стратегию валидации и план разработки.

### 1.2 Контекст

На территории завода функционирует несколько автомоек с различной пропускной способностью, географическим расположением и спецификацией. Водители корпоративного транспорта (легковые, грузовые, автобусы) направляются на мойку без централизованного диспетчирования, что приводит к:

- неравномерной загрузке отдельных моек (перегрузка vs. простой);
- длительному времени ожидания в очередях;
- избыточному времени в пути до удалённых моек;
- потере производительности транспортного парка предприятия.

### 1.3 Границы системы

| Входит в систему | Не входит в систему |
|---|---|
| Диспетчерский алгоритм распределения | Биллинг, оплата, CRM клиентов |
| Визуальный симулятор | Управление оборудованием моек (IoT) |
| Модуль аналитики и отчётности | GPS-трекинг в реальном времени (интеграция) |
| API для приёма заявок на мойку | Разработка мобильных приложений для водителей |
| Система сбора исторических данных | Видеонаблюдение |
| Приоритетные очереди (без вытеснения) | Preemption — прерывание начатой мойки |

### 1.4 Ключевые проектные решения (Design Decisions)

Эти решения зафиксированы в версии 2.0 и являются фундаментом системы. Изменение любого из них требует пересмотра документа.

| # | Решение | Обоснование |
|---|---------|-------------|
| D-1 | **Core-First**: ядро — чистый TypeScript-пакет без зависимостей от UI, сети и БД | Одно ядро для симулятора и будущего production-диспетчера; логика не «прирастает» к React |
| D-2 | **Simulation-First**: симулятор — первый продукт, production API — на его основе | Алгоритмы валидируются на исторических данных до вывода в эксплуатацию |
| D-3 | **Discrete-Event Simulation** вместо дискретного времени | Точность и скорость: пустые интервалы пропускаются, легко достижим 1000x (NF-06) |
| D-4 | **Детерминизм**: все случайности через seeded PRNG | Воспроизводимость прогонов — обязательное условие A/B-сравнения алгоритмов |
| D-5 | **Гетерогенное обслуживание**: время мойки зависит от типа ТС | Реальность ближе к M/G/c; однородная μ искажает оценки в разы |
| D-6 | **Совместимость — жёсткое ограничение ядра**, а не параметр алгоритма | Алгоритм физически не может назначить ТС на несовместимую мойку |

## 2. Постановка задачи

### 2.1 Задача в общем виде

Построить интеллектуальную систему, которая для каждого нового запроса на мойку выбирает **оптимальную автомойку** из доступных, минимизируя суммарное время системы для водителя:

$$
T_{total} = T_{travel} + T_{wait} + T_{service}
$$

где:
- $T_{travel}$ — время в пути от текущего местоположения до мойки;
- $T_{wait}$ — ожидаемое время ожидания в очереди;
- $T_{service}$ — ожидаемое время обслуживания (зависит от типа ТС, см. 3.5).

При этом система должна:
1. Максимизировать загрузку всех моек (избегать простоя);
2. Минимизировать среднее время ожидания по сети;
3. Учитывать приоритеты (срочные рейсы, VIP-транспорт);
4. Быть устойчивой к всплескам нагрузки (смены, погода, пятницы);
5. Обеспечивать справедливое распределение (не «забивать» одну мойку постоянно);
6. Учитывать эффект «стада»: машины, уже едущие к мойке, увеличивают её будущую нагрузку (см. 7.3).

### 2.2 Пространственная модель

Территория завода моделируется как плоская сетка координат в метрах. Мойки и точки появления заявок имеют координаты $(x, y)$.

**Расстояние.** По умолчанию используется **манхэттенская метрика** (дороги завода, как правило, ортогональны):

$$
d_{ij} = |x_i - x_j| + |y_i - y_j|
$$

Опционально — евклидова метрика. Метрика задаётся в конфигурации симуляции. Полноценный граф дорог — вне скоупа MVP (возможное расширение на этапе 4–5).

**Время в пути:**

$$
T_{travel} = \frac{d}{v_{avg}}
$$

где $v_{avg}$ — средняя скорость ТС по территории завода (конфигурируемый параметр, по умолчанию 20 км/ч).

## 3. Математическая модель

### 3.1 Базовые параметры

| Параметр | Обозначение | Описание | Единицы |
|----------|-------------|----------|---------|
| Интенсивность поступления | $\lambda$ | Сколько машин приходит в единицу времени (может зависеть от времени суток, $\lambda(t)$) | машин/час |
| Интенсивность обслуживания | $\mu_t$ | Сколько машин типа $t$ может обработать один пост в единицу времени | машин/час |
| Время обслуживания | $T_{service,t} = 1/\mu_t$ | Среднее время мойки ТС типа $t$ | минуты |
| Число постов | $c$ | Количество одновременно работающих постов | шт. |
| Коэффициент загрузки | $\rho$ | $\rho = \frac{\lambda}{c\bar{\mu}}$ | доля (0–1) |
| Среднее время ожидания | $W_q$ | Сколько в среднем машина ждёт в очереди | минуты |
| Средняя длина очереди | $L_q$ | $L_q = \lambda W_q$ (Little's Law) | машин |
| Время в пути | $T_{travel}$ | $d / v_{avg}$ (см. 2.2) | минуты |
| Машины в пути к мойке | $n_{transit}$ | Назначены мойке, но ещё не прибыли | машин |

### 3.2 Модель M/M/c

Каждая автомойка в первом приближении моделируется как многоканальная система массового обслуживания **M/M/c**:

- **Первая M** — Markovian arrivals: поток заявок — Пуассоновский процесс с интенсивностью $\lambda$ (в реальности $\lambda(t)$ меняется в течение суток, см. Приложение Б);
- **Вторая M** — Markovian service: время обслуживания — экспоненциальное распределение со средним $1/\mu$;
- **c** — число параллельных каналов (постов мойки).

**Условие стабильности:**

$$
\rho = \frac{\lambda}{c\mu} < 1
$$

При $\rho \to 1$ очередь растёт нелинейно: разница между $\rho = 0.8$ и $\rho = 0.95$ по времени ожидания — кратная, а не процентная. Алгоритмы обязаны учитывать этот эффект (штраф за $\rho > 0.9$).

### 3.3 Формула Erlang C

Вероятность того, что прибывшая машина попадёт в очередь (все $c$ постов заняты):

$$
P_{wait} = \frac{\frac{(c\rho)^c}{c!(1-\rho)}}{\sum_{k=0}^{c-1}\frac{(c\rho)^k}{k!} + \frac{(c\rho)^c}{c!(1-\rho)}}
$$

**Среднее время ожидания в очереди:**

$$
W_q = \frac{P_{wait}}{c\mu - \lambda}
$$

**Среднее количество машин в очереди (Little's Law):**

$$
L_q = \lambda \cdot W_q
$$

Численно устойчивый псевдокод — в Приложении А.

### 3.4 Ограничения модели M/M/c: гетерогенное обслуживание

M/M/c предполагает одинаковое распределение времени обслуживания для всех заявок. В реальности:

```text
🚙 легковая       → ~8 мин
🚚 грузовая       → ~25 мин
🚌 автобус        → ~40 мин
```

Поэтому фактическая модель ближе к **M/G/c** (произвольное распределение времени обслуживания), для которой точных замкнутых формул нет. Принятое в проекте соглашение:

1. **Симулятор — эталон истины.** Время обслуживания каждой заявки генерируется по типу ТС из конфигурации мойки (`serviceTimeMin`, см. 8.1).
2. **Erlang C — аналитическая оценка.** Для быстрых оценок $W_q$ в алгоритмах (State-Aware Score) используется Erlang C с **эффективной интенсивностью обслуживания** — гармоническим средним по долям типов в потоке:

$$
\bar{\mu} = \frac{1}{\sum_t p_t \cdot \frac{1}{\mu_t}}
$$

где $p_t$ — доля ТС типа $t$ в потоке заявок.

3. Валидация (раздел 12.3) проверяет сходимость симуляции к теории на однородном потоке (один тип ТС), где M/M/c точна.

### 3.5 Эффективная нагрузка (Effective Load)

Для сравнения моек с разными параметрами вводится эффективная нагрузка — ожидаемое время до начала обслуживания новой заявки с учётом машин в пути:

$$
L_{eff,i} = \frac{queue_i + busy_i + n_{transit,i}}{c_i} \cdot \frac{1}{\bar{\mu}_i}
$$

где:
- $queue_i$ — машин в очереди;
- $busy_i$ — занятых постов;
- $n_{transit,i}$ — машин, назначенных мойке $i$, но ещё не прибывших (защита от herd-эффекта, см. 7.3);
- $\bar{\mu}_i$ — эффективная интенсивность обслуживания.

### 3.6 Полная оценка для выбора мойки

Для каждой мойки $i$ вычисляется **score** (меньше = лучше):

$$
Score_i = \alpha \cdot W_{q,i} + \beta \cdot T_{travel,i} + \gamma \cdot T_{service,i} + \delta \cdot \rho_i
$$

где $\alpha, \beta, \gamma, \delta$ — настраиваемые веса, $\alpha + \beta + \gamma + \delta = 1$. Это общая форма; конкретные алгоритмы (раздел 7) являются её частными случаями или альтернативами.

### 3.7 Дисциплина очереди

- **По умолчанию — FIFO** в рамках каждого приоритетного класса.
- **Приоритетный режим (F-06):** взвешенная приоритетная очередь — `urgent` обгоняет `normal`, `normal` обгоняет `scheduled`. Порядок внутри класса — FIFO.
- **Preemption (прерывание начатой мойки) — вне скоупа системы.** Начатое обслуживание всегда доводится до конца.
- Приоритет влияет на **порядок обслуживания**, но не на **выбор мойки**: мойка выбирается алгоритмом единообразно для всех приоритетов (иначе urgent-заявки будут дестабилизировать баланс).

## 6. Архитектура системы

### 6.1 Архитектурный принцип: Core-First

Главное архитектурное решение проекта (D-1, D-2): **вся предметная логика сосредоточена в изолированном пакете `packages/core`**, который ничего не знает о браузере, React, HTTP или базе данных. Симулятор и будущий production-диспетчер — это две разные «оболочки» над одним ядром.

```text
┌──────────────────────────────────────────────────────────────┐
│                        MONOREPO (pnpm workspaces)            │
│                                                              │
│  ┌────────────────────────────────────────────────────┐     │
│  │                 packages/core                       │     │
│  │  ┌────────────┐ ┌────────────┐ ┌────────────────┐  │     │
│  │  │   Domain   │ │ Dispatcher │ │    Algorithm   │  │     │
│  │  │   Model    │ │            │ │    Engine      │  │     │
│  │  └────────────┘ └────────────┘ └────────────────┘  │     │
│  │  ┌────────────┐ ┌────────────┐ ┌────────────────┐  │     │

```

**Что это даёт:**

1. Алгоритм, проверенный в симуляторе, гарантированно тот же, что работает в production — нет риска расхождения реализаций.
2. Ядро тестируется изолированно и быстро (Vitest, без браузера).
3. UI можно радикально менять, не трогая логику; логику — не трогая UI.

**Правило зависимостей:** `simulator → core`, `api → core`. Обратных зависимостей быть не может. В `core` запрещены импорты DOM, `window`, `fs`, HTTP-клиентов (NF-11).

### 6.2 Компоненты системы

1. **Request Source** — API или ручной ввод заявок на мойку; в симуляторе — CSV-файл или генератор.
2. **Dispatcher (Core)** — принимает заявку, запрашивает снапшот состояния моек, вызывает активный алгоритм, маршрутизирует заявку, пишет в журнал решений (F-09). Решение < 100 мс (NF-01).
3. **Algorithm Engine (Pluggable)** — взаимозаменяемые реализации интерфейса `LoadBalancingAlgorithm` (см. 7.1).
4. **Simulation Engine (DES)** — движок дискретно-событийной симуляции (см. 6.3).
5. **State & Metrics** — длины очередей, занятые посты, $n_{transit}$, исторический $\lambda$, расчёты Erlang C.
6. **Visual Simulator (Frontend)** — Canvas-карта, дашборды метрик, A/B-сравнение, replay исторических данных.

### 6.3 Движок симуляции: Discrete-Event Simulation

Вместо дискретного времени (fixed timestep) используется **DES**: симуляционные часы перескакивают от события к событию, пропуская пустые интервалы.

**Типы событий:**

| Событие | Описание |
|---------|----------|
| `ARRIVAL` | Появление заявки → решение диспетчера → машина выезжает |
| `WASH_ARRIVED` | Машина прибыла на мойку → в очередь или на свободный пост |
| `SERVICE_START` | Машина с головы очереди заняла освободившийся пост |
| `SERVICE_COMPLETE` | Мойка завершена → пост освобождается → запуск следующего из очереди |
| `POST_FAILURE` | Пост вышел из строя (F-08) |
| `POST_RECOVER` | Пост восстановлен |

**Цикл движка (псевдокод):**

```text
eventQueue = PriorityQueue<Event>(by: time)
while eventQueue.notEmpty and clock < simEnd:
    event = eventQueue.pop()
    clock = event.time
    handle(event)           # обновляет состояние
    schedule(newEvents)     # порождает новые события (все случайности — через PRNG)
    metrics.record(clock, state)
```

**Почему DES, а не дискретное время:**

- **Точность:** события происходят в их истинные моменты времени, нет ошибки дискретизации шага $\Delta t$.
- **Скорость:** ночные часы без заявок обрабатываются нулём итераций — требование 1000x (NF-06) достигается естественно.
- **Корректная статистика:** time-weighted метрики ($\rho$, $L_q$) считаются точно, без усреднения по шагам.

**Детерминизм (NF-10):** единственный источник случайности в ядре — инжектируемый seeded PRNG (mulberry32). Генератор arrivals, времена обслуживания, отказы постов, случайные выборы в алгоритмах (Random, Power of d) — всё через этот PRNG. `Math.random()` в ядре запрещён (проверяется линтером).

### 6.4 Поток данных

```text
1. Заявка поступает → Request Source
2. Dispatcher фильтрует мойки по совместимости (F-07) и активности
3. Dispatcher запрашивает снапшот: очереди, busy-посты, n_transit, λ, ρ
4. Алгоритм вычисляет Score для каждого кандидата → Decision
5. Мойка резервируется: n_transit += 1 (машина «в пути»)
6. Событие фиксируется → State Store + Event Log (F-09)
7. По прибытии машины (WASH_ARRIVED): n_transit -= 1, очередь += 1
8. Simulator (если активен) получает обновление состояния
9. Analytics обновляет агрегаты
```

## 7. Алгоритмы балансировки нагрузки

### 7.1 Контракт алгоритма

Все алгоритмы реализуют единый интерфейс (NF-09). Ядро гарантирует: алгоритм видит **только совместимые и активные мойки** — фильтрация по F-07 выполняется до вызова.

```typescript
interface LoadBalancingAlgorithm {
    readonly name: string;

    decide(ctx: DecisionContext): Decision;
}

interface DecisionContext {
    request: WashRequest;          // тип ТС, приоритет, координаты
    candidates: WashSnapshot[];    // только совместимые активные мойки
    now: SimTime;
    rng: Rng;                      // seeded PRNG — единственный источник случайности
}

interface WashSnapshot {
    washId: string;
    queueLength: number;           // L_q сейчас
    busyPosts: number;
    totalPosts: number;            // c
    inTransit: number;             // n_transit — едут к этой мойке
    serviceTimeMin: ServiceTimes;  // T_service по типам ТС
    rho: number;
    expectedWaitMin: number;       // W_q по Erlang C с μ̄
    travelTimeMin: number;         // T_travel от точки заявки
}

interface Decision {
    washId: string | null;         // null — отказ (нет кандидатов)
    scores: Record<string, number>; // score по каждому кандидату — для журнала F-09
}
```

Возвращённый `scores` пишется в журнал решений: любое решение можно воспроизвести и объяснить постфактум.

### 7.2 Сводная таблица

| Алгоритм | Учитывает очередь | Учитывает $\mu$ | Учитывает $c$ | Учитывает $n_{transit}$ | Учитывает расстояние | Прогноз | Сложность |
|----------|-------------------|-----------------|---------------|--------------------------|----------------------|---------|-----------|
| Random | Нет | Нет | Нет | Нет | Нет | Нет | $O(1)$ |
| Round Robin | Нет | Нет | Нет | Нет | Нет | Нет | $O(1)$ |
| Least Connections | Да (частично) | Нет | Нет | Нет | Нет | Нет | $O(n)$ |
| **JSQ** | Да | Нет | Нет | Да | Нет | Нет | $O(n)$ |
| **Weighted JSQ** ⭐ | Да | Да | Да | Да | Да (опц.) | Нет | $O(n)$ |
| **Power of d=2** ⭐ | Да | Да | Да | Да | Да | Нет | $O(d)$ |
| **State-Aware Score** ⭐ | Да | Да | Да | Да | Да | Нет | $O(n)$ |
| Predictive | Да | Да | Да | Да | Да | Да | $O(n \cdot T)$ |

### 7.3 Herd-эффект и машины в пути

Классическая проблема JSQ-подобных алгоритмов: несколько заявок, обработанных почти одновременно, видят одинаковое состояние и все направляются на одну «лучшую» мойку. К моменту их прибытия она уже перегружена.

**Решение, зафиксированное в ядре (F-11):** мойка резервируется в момент решения — счётчик $n_{transit,i}$ увеличивается сразу и уменьшается по прибытии машины. Все алгоритмы, учитывающие очередь, обязаны использовать эффективную длину:

$$
queue_{eff,i} = queue_i + busy_i + n_{transit,i}
$$

Это устраняет herd-эффект без обмена сообщениями между заявками.

### 7.4 Спецификация алгоритмов

#### 7.4.1 Random (Baseline)
```text
return candidates[rng.int(0, n - 1)]
```
**Назначение:** точка отсчёта. Любой осмысленный алгоритм должен превосходить Random на одних и тех же данных (проверяется в A/B-режиме).

#### 7.4.2 Round Robin
```text
counter = (counter + 1) % n
return candidates[counter]
```
**Назначение:** статическое распределение, учебная ступень. Не учитывает состояние.

#### 7.4.3 Join Shortest Queue (JSQ)
```text
return argmin_i (queue_i + busy_i + inTransit_i)
```
**Назначение:** классика теории очередей. Хорош для однородных моек; в базовой форме не различает мойки по $\mu$ и $c$.

#### 7.4.4 Weighted JSQ ⭐ (Primary)
```text
for each candidate i:
    L_eff_i = (queue_i + busy_i + inTransit_i) / c_i * (1 / μ̄_i)
    score_i = L_eff_i + w_travel * travelTime_i
return argmin_i (score_i)
```
**Назначение:** **основной production-алгоритм.** Оценивает ожидаемое время до начала обслуживания с учётом разной пропускной способности моек и времени в пути.

#### 7.4.5 Power of d Choices (d=2) ⭐ (Primary)
```text
candidates2 = rng.sample(candidates, d=2)
return argmin_i∈candidates2 (score_i)   // score — как в Weighted JSQ
```
**Назначение:** компромисс между качеством и накладными расходами. Даже $d=2$ радикально лучше Random. Пригоден при большом числе моек и устаревании снапшотов.

#### 7.4.6 State-Aware Score ⭐ (Primary)
```text
score_i = α·W_q(i) + β·travelTime_i + γ·(1/μ̄_i) + δ·ρ_i + ε·penalty_i

где:
  W_q(i)  = Erlang C ожидание (с μ̄)
  penalty_i = 0,                если ρ_i ≤ 0.9
            = P_over · (ρ_i - 0.9) / 0.1,   если ρ_i > 0.9
  α,β,γ,δ,ε — настраиваемые веса (Σα..δ = 1)
return argmin_i (score_i)
```
**Назначение:** наиболее гибкий алгоритм; веса подбираются на симуляторе (S-08). Штраф за перегрузку отражает нелинейный рост очереди при $\rho \to 1$.

#### 7.4.7 Predictive Load Balancer (Future, этап 4)
```text
for each candidate i:
    score_i = α · currentLoad_i + β · forecastLoad_i(horizon)
return argmin_i (score_i)
```
**Назначение:** учитывает предстоящие пики (смены, обед, пятница). Прогноз — скользящее среднее по историческому $\lambda(t)$ с суточным профилем.

## 9. Спецификация визуального симулятора

### 9.1 Назначение

Симулятор — это **инструмент валидации и исследования** (D-2). Он позволяет:

1. Прогонять исторические данные через разные алгоритмы;
2. Визуально наблюдать поведение системы;
3. Сравнивать алгоритмы по метрикам на **одном seed и одних данных** (A/B);
4. Проводить «what-if» анализ;
5. Генерировать отчёты для принятия решений.

Симулятор — тонкая оболочка над `packages/core`: вся логика (DES, диспетчер, алгоритмы, метрики) живёт в ядре, UI только подписывается на снапшоты состояния.

### 9.2 Экраны симулятора

#### Экран 1: Конфигурация
- Загрузка CSV с историческими данными и конфигурацией моек;
- Генерация синтетических arrivals с заданным seed (S-11);
- Настройка параметров симуляции (`SimConfig`): алгоритм, веса, seed, метрика расстояния, средняя скорость;
- Карта завода с drag-and-drop размещением моек.

#### Экран 2: Симуляция (основной)
- **Карта** (Canvas): мойки, очереди, машины в пути (визуально отличимы от стоящих в очереди);
- **Панель метрик**: $\rho$, $W_q$, $L_q$, $n_{transit}$ для каждой мойки в реальном времени;
- **Графики**: динамика очередей, загрузки, среднего времени ожидания;
- **Управление**: play/pause, скорость (1x–100x), headless-прогон «до конца» без рендера;
- **Лог событий**: таблица с каждым решением диспетчера и score кандидатов.

#### Экран 3: Сравнение алгоритмов (A/B)
- Запуск двух алгоритмов на одних и тех же данных и **одном seed** (NF-10 гарантирует идентичность входного потока);
- Сравнительные графики;
- Итоговая таблица метрик с целевой функцией (12.2).

#### Экран 4: Отчёт
- Сводка по симуляции;
- Экспорт графиков (PNG);
- Экспорт лога решений (CSV);
- Рекомендации по оптимизации.

### 10.5 Обоснование выбора и отклонённые альтернативы

> **Почему единый TypeScript-стек?**
>
> Главный аргумент — решение D-1: ядро должно исполняться и в браузере (симулятор), и на сервере (production-диспетчер). Единственный способ гарантировать, что алгоритм, проверенный на исторических данных, бит-в-бит совпадает с боевым — **одна реализация на одном языке**.

> **Почему не Python (NumPy/SimPy) для симуляции?**
>
> Python силён в аналитике, но: (1) появляется второй язык и вторая реализация алгоритмов — классический источник расхождений; (2) интерактивный браузерный симулятор всё равно потребовал бы JS; (3) DES на чистом TS достаточно быстр для наших масштабов (≤ 20 моек, тысячи заявок).

> **Почему не Rust/WASM для ядра?**
>
> Избыточно на данном этапе: вычислительная нагрузка мала (события, а не физика), а порог входа и скорость итераций важнее. Если этап 4 (прогнозирование) упрётся в производительность — пересмотрим.

## 12. Метрики, KPI и валидация

### 12.1 Ключевые метрики системы

| Метрика | Формула | Целевое значение |
|---------|---------|-----------------|
| Среднее время ожидания | $\bar{W}_q = \frac{1}{N}\sum W_q$ | < 5 мин |
| Максимальное время ожидания | $\max(W_q)$ | < 15 мин |
| Доля нарушений SLA ожидания | $P(W_q > 15\text{ мин})$ | < 5% |
| Средняя загрузка | $\bar{\rho} = \frac{1}{n}\sum \rho_i$ | 70–85% |
| Коэффициент вариации загрузки | $CV = \sigma_\rho / \bar{\rho}$ | < 0.3 |
| Среднее время в пути | $\bar{T}_{travel}$ | Минимально возможное |
| Процент отказов (нет кандидатов) | $P_{reject} = N_{reject}/N_{total}$ | < 1% |
| Справедливость (Jain's fairness) | $J = \frac{(\sum x_i)^2}{n \sum x_i^2}$ | > 0.8 |

### 12.2 Сравнение алгоритмов

Для сравнения алгоритмов фиксируется **один и тот же набор данных и один seed**; замеряются метрики 12.1. Лучший алгоритм минимизирует:

$$
Objective = 0.5 \cdot \bar{W}_q + 0.3 \cdot \bar{T}_{travel} + 0.2 \cdot CV_{\rho}
$$

Обязательное условие: любой алгоритм, претендующий на production, должен превосходить Random по целевой функции на том же наборе данных.

### 12.3 Валидация математики

Доверие к симулятору достигается проверкой сходимости к теории там, где теория точна (однородный поток, один тип ТС → M/M/c):

1. **Unit-тесты Erlang C:** реализация сверяется с опубликованными табличными значениями. Контрольные точки:

| $\lambda$ | $\mu$ | $c$ | $\rho$ | $P_{wait}$ (Erlang C) |
|-----------|-------|-----|--------|------------------------|
| 8 | 5 | 2 | 0.8 | 0.711 |
| 12 | 5 | 3 | 0.8 | 0.647 |
| 16 | 5 | 4 | 0.8 | 0.596 |

2. **Валидация DES:** долгий прогон одной изолированной мойки ($\rho \in \{0.7, 0.8, 0.9\}$, однородный поток, ≥ 10 000 заявок) — эмпирические $\bar{W}_q$, $\bar{L}_q$ обязаны сойтись к теоретическим значениям Erlang C в допуске ±5%.
3. **Property-тесты:**
   - $\rho \geq 1$ → очередь растёт неограниченно (нестабильность обнаруживается);
   - закон сохранения: сумма потоков по мойкам равна входному потоку минус отказы;
   - при нулевом потоке все метрики равны нулю.
4. **Тест детерминизма:** два прогона с одинаковым `SimConfig.seed` дают идентичный `decisions.csv`.

## 13. Приложения

### Приложение А. Формула Erlang C (псевдокод, численно устойчивый)

```typescript
// packages/core: erlang-c.ts
// Численная устойчивость достигается рекуррентным вычислением Erlang B
function erlangC(lambda: number, mu: number, c: number): number {
    const rho = lambda / (c * mu);
    if (rho >= 1) return 1.0; // нестабильная система

    // Erlang B (вероятность блокировки) — рекуррентно, без факториалов
    let erlangB = 1.0;
    for (let k = 1; k <= c; k++) {
        erlangB = (rho * c * erlangB) / (k + rho * c * erlangB);
    }

    return erlangB / (1 - rho + rho * erlangB);
}

// W_q в тех же единицах времени, что и 1/mu
function expectedWait(lambda: number, mu: number, c: number): number {
    const pw = erlangC(lambda, mu, c);
    return pw / (c * mu - lambda);
}
```

### Приложение Б. Генератор тестовых данных

Синтетические arrivals генерируются нестационарным Пуассоновским процессом с суточным профилем (S-11). Все случайные величины — через seeded PRNG.

```text
Профиль интенсивности λ(t), доля от базового λ_base:

00–07:  0.2 × λ_base     (ночь)
07–10:  2.5 × λ_base     (утренний пик, начало смены)
10–12:  1.0 × λ_base
12–13:  0.5 × λ_base     (обеденный спад)
13–16:  1.0 × λ_base
16–19:  2.0 × λ_base     (вечерний пик, конец смены)
19–24:  0.4 × λ_base

Пятница: дополнительный множитель 1.3 к вечернему пику.
```

Псевдокод (thinning-метод Льюиса для нестационарного процесса):

```text
λ_max = max_t λ(t)
t = 0
while t < horizon:
    t += rng.exponential(λ_max)
    if rng.next() < λ(t) / λ_max:
        emit(arrival(t, type=weightedRandom(rng), x, y))
```
