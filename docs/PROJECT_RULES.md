# Правила ведения проекта Load Balancer

> Этот документ фиксирует рабочие соглашения команды. Все участники и AI-агенты обязаны им следовать.

## 1. Git: фиксируем результат вовремя

### 1.1 Commit после каждой законченной задачи

- Как только задача выполнена и проверена (тесты зелёные, typecheck проходит, ручная проверка сделана) — **сразу делай commit**.
- Не откладывай commit «на вечер» и не копи несохранённые изменения.
- Commit должен содержать логически завершённый кусок работы.

### 1.2 Сообщения коммитов

Формат:

```text
<тип>: <краткое описание>

[опциональное тело]
```

Типы:

| Тип | Когда использовать |
|---|---|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `test` | Добавление или исправление тестов |
| `refactor` | Рефакторинг без изменения поведения |
| `docs` | Изменения только в документации |
| `chore` | Сборка, зависимости, инфраструктура |

Примеры:

```text
feat: DES-движок и диспетчер для core

- events: ARRIVAL, WASH_ARRIVED, SERVICE_START, SERVICE_COMPLETE
- фильтр совместимости F-07 до вызова алгоритма
- журнал решений F-09
```

```text
test: unit-тесты Erlang C против табличных значений
```

### 1.3 Push в удалённый репозиторий

- После завершения задачи и commit — **сразу push** в текущую ветку.
- Если работаешь над фичей в отдельной ветке — push её, чтобы состояние было доступно команде.
- Перед push проверяй, что не отправляешь мусор: `pnpm -r test` и `pnpm -r typecheck` зелёные.

### 1.4 Не оставляй рабочую директорию в грязи

- `.decisions-*.csv`, логи сборки и временные файлы — либо добавляй в `.gitignore`, либо удаляй перед commit.
- `node_modules` уже в `.gitignore`; не коммить их.

## 2. Разработка: core-first

- Вся предметная логика — в `packages/core`. UI (`packages/simulator`) и API (`packages/api`) — тонкие оболочки.
- Не импортируй DOM, `window`, `fs`, `Math.random()`, `Date.now()` в `packages/core`.
- Любая новая фича начинается с ядра и тестов, только потом — с UI.

## 3. Качество кода

- TypeScript strict. `pnpm -r typecheck` должен проходить.
- Для `packages/core` — unit-тесты на новый функционал.
- Для исправлений багов — сначала тест, воспроизводящий баг, потом фикс.
- Не коммить код с `console.log` и отладочными `debugger` без причины.

## 4. Документация

- При изменении архитектуры, сборки или команд — обновляй `AGENTS.md`.
- Новые модули желательно сопровождать коротким `README.md` или разделом в `docs/`.
- Комментарии в коде — на русском (технические термины на английском).

## 5. Рабочий процесс

1. Взял задачу → короткий план/список шагов.
2. Реализовал → проверил тесты и typecheck.
3. Обновил документацию, если требуется.
4. `git add -p` или `git add` по файлам → `git commit` → `git push`.
5. В сообщении к задаче/PR — кратко, что сделано и как проверить.

## 6. Что считать "задачей"

- Законченный коммит: один логический шаг, который можно влить в основную ветку без поломки.
- Не обязательно ждать «идеала», но обязательно — работающего состояния.
